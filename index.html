00 · Installation and project setup

Yes—installation belongs in a complete learning path. The official docs recommend starting with create-next-app, then learning the App Router conventions.

Prerequisites

  • Comfort with HTML, CSS, JavaScript and React.
  • Install a supported Node.js version. The current installation guide lists Node.js 20.9+; verify requirements when upgrading.
  • Use a package manager such as npm, pnpm, Yarn or Bun.

First run checklist

  1. Create the app and run npm run dev.
  2. Edit app/page.tsx and confirm hot reload works.
  3. Understand app/layout.tsx and the required root html/body.
  4. Create one route, one dynamic route and one shared component.
  5. Run lint/type checks and npm run build before deploying.

01 · Why Next.js?

Next.js is a React framework that adds routing, server rendering, data-fetching patterns, backend endpoints and production optimizations around React.

React alone

Primarily a UI library. You choose and assemble routing, rendering strategy, data patterns, SEO setup and build tooling.

Next.js

A framework with file-based routing, Server Components, server rendering, streaming, metadata APIs, image/font optimization and deployment conventions.

Why teams choose it

  • SEO and first load: server-rendered or prerendered HTML can make meaningful content available before client JavaScript finishes.
  • Flexible rendering: choose static/prerendered output or request-time data where the page needs it.
  • Full-stack workflow: use Route Handlers and Server Actions for appropriate backend tasks.
  • Performance defaults: route prefetching, streaming, image/font tooling and code splitting.
Interview answer: “I use Next.js when a React app benefits from integrated routing, server rendering, SEO metadata, data access and production conventions. I still choose the rendering and caching strategy per route instead of assuming every page should be static or dynamic.”

03 · Routing and dynamic routes

In the App Router, folders define URL segments; special files define what each segment does.

app/
  layout.tsx             # required root layout
  page.tsx               # /
  about/page.tsx         # /about
  blog/[slug]/page.tsx   # /blog/hello-world
  shop/[...parts]/page.tsx      # one or more segments
  docs/[[...slug]]/page.tsx     # zero or more segments
  not-found.tsx
  loading.tsx
  error.tsx
ConventionPurposeInterview note
page.tsxPublicly accessible UI for a route.Folder alone does not expose a page; a page/route handler is needed.
layout.tsxShared UI around child routes.Layouts preserve state and remain interactive across navigation.
loading.tsxSegment-level loading UI.Creates a Suspense boundary for the route segment.
error.tsxSegment error fallback.Must be a Client Component; catches errors in its child segment.
not-found.tsxNot-found UI.Use notFound() for a missing resource.
route.tsHTTP endpoint.Cannot coexist with page.tsx at the exact same route segment.

Read dynamic parameters

// app/blog/[slug]/page.tsx (current App Router pattern)
export default async function BlogPost({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const post = await getPostBySlug(slug)

  if (!post) notFound()
  return <article><h1>{post.title}</h1></article>
}
  • [slug]: one dynamic segment.
  • [...slug]: catch-all; requires one or more segments.
  • [[...slug]]: optional catch-all; also matches the parent path.
  • params describes path segments; searchParams describes query-string values like ?page=2.
  • Use Link for normal navigation; use useRouter for imperative navigation in a Client Component.

Other routing conventions worth knowing

  • (group) route groups organize files without changing the URL.
  • @slot defines a parallel route slot, useful for multi-panel layouts and independent sections.
  • (.), (..) and related intercepting-route conventions can render another route within the current layout context—useful for modal navigation patterns.
  • template.tsx is similar to a layout but remounts its children on navigation; choose it when fresh state/effects are required.
  • default.tsx provides a fallback for an unmatched parallel route slot.
  • generateStaticParams() can generate dynamic route params for prerendering. Understand its interaction with dynamic rendering and current caching features.
  • redirect() redirects during rendering/actions; useRouter is for imperative client navigation. Validate user-controlled destinations.
Common trap: In current App Router docs, params and page searchParams are promises—await them. Older tutorials may show synchronous props.

04 · Linking, navigation and prefetching

Next.js navigation is client-side by default: <Link> swaps the changed route segments without a full document reload, while shared layouts keep their state.

APIWhereUse for
<Link href>Server or ClientDefault navigation; renders an <a>, so it is crawlable and accessible.
useRouter()Client onlypush, replace, back, refresh, prefetch after an event.
usePathname()Client onlyActive-link styling, analytics.
useSearchParams()Client onlyRead query string; wrap the reader in <Suspense> on prerendered routes.
useParams()Client onlyRead dynamic segments inside nested Client Components.
redirect() / permanentRedirect()Server (render, action, handler)Server-side redirects (307/308-style); throws, so do not wrap in try/catch.
// components/nav-link.tsx
'use client'
import Link from 'next/link'
import { usePathname } from 'next/navigation'

export function NavLink({ href, children }) {
  const pathname = usePathname()
  const active = pathname === href
  return (
    <Link href={href} aria-current={active ? 'page' : undefined}>
      {children}
    </Link>
  )
}

Prefetching in one paragraph

In production, <Link> prefetches routes as they enter the viewport. Static routes can be prefetched fully; dynamic routes are prefetched up to the nearest loading.tsx, so the loading UI can appear instantly. Prefetching is disabled in development. Turn it off with prefetch={false} for huge link lists where it wastes bandwidth.

Soft vs hard navigation

Soft (client)

Only changed segments re-render, layouts and client state are kept, scroll moves to the top of the new segment. Triggered by Link / router.push.

Hard (full reload)

Plain <a>, window.location, or navigating across different root layouts. All client state is lost.

Interview tip: "Why does my URL state reset?" → probably a hard navigation or a template.tsx. "How do I keep filters in the URL?" → write them to searchParams with router.replace so the page is shareable and the server can read them.

05 · Server Components vs Client Components

Server Component (default)

  • Runs on the server.
  • Can await data and query a database directly.
  • Can keep secrets server-side when used correctly.
  • Good for read-heavy UI and reducing browser JavaScript.
No useState / onClick

Client Component

  • Opt in with 'use client' at the file boundary.
  • Use state, effects, event handlers and browser APIs.
  • Its JavaScript is sent to the browser.
  • Good for interactive widgets, menus, forms and charts.
Interactive UI

Decision flow

Need state, event handlers, effects or browser APIs?
→
Yes
Client Component for that small boundary
No
Keep it a Server Component
// Server Component: app/products/page.tsx
import ProductFilter from './product-filter'

export default async function ProductsPage() {
  const products = await getProducts()
  return <>
    <h1>Products</h1>
    <ProductFilter products={products} />
  </>
}

// product-filter.tsx
'use client'
import { useState } from 'react'
export default function ProductFilter({ products }) {
  const [query, setQuery] = useState('')
  return <>
    <input value={query} onChange={e => setQuery(e.target.value)} />
    {/* render filtered products */}
  </>
}

Rule of thumb: keep the client boundary as low and small as practical. Server Components can render Client Components, and Client Components can receive server-rendered UI as children/props where serializable. Do not pass database clients, secrets or arbitrary non-serializable values to the client.

Composition patterns interviewers ask about

// 1. Server content inside a Client wrapper: pass it as children
// app/layout.tsx (Server)
<Modal><ServerRenderedCart /></Modal>   // Modal is 'use client'

// 2. Context providers must be Client Components — wrap once, high up
// app/providers.tsx
'use client'
export function Providers({ children }) {
  return <ThemeProvider>{children}</ThemeProvider>
}

// 3. Guarantee a module never ends up in the browser bundle
// lib/data.ts
import 'server-only'   // build error if imported from a Client Component
Can I…Answer
Import a Server Component into a Client Component file?No — it becomes client code. Pass it as children/props instead.
Pass a function prop from Server to Client?Only a Server Action ('use server'). Regular functions are not serializable.
Pass a Date, Map or Promise?React can serialize many built-ins including Dates, Maps, Sets and Promises (consume with use()); class instances are not supported.
Use async Client Components?No. Fetch in a parent Server Component or use a client data library.
Do Client Components render on the server?Yes, for the initial HTML. 'use client' means "also ships to and hydrates in the browser", not "browser only".
Classic trap: 'use client' marks a boundary. Everything imported by that file joins the client bundle, so placing it in a top-level layout silently turns the whole tree into client code.

06 · SSR, SSG, ISR and CSR

TermWhen HTML/data is producedBest fitTrade-off
SSRAt request time on the server.Request-specific or frequently changing content.Server work on requests; latency depends on data.
SSG / prerenderingBefore requests, commonly at build time.Stable public pages.Needs a strategy to refresh stale content.
ISR / revalidationServe reusable output and refresh according to configured revalidation.Content that can be briefly stale.Understand freshness windows and on-demand invalidation.
CSRBrowser JavaScript fetches/renders data.Highly interactive, browser-only experiences.May delay meaningful content; SEO/initial loading needs care.
StreamingSend UI in chunks as parts become ready.Pages with slow or independent data sections.Requires good loading boundaries and thoughtful UX.

These are useful conceptual labels, not four mutually exclusive switches. A Next.js route can combine server rendering, prerendered pieces, client interactivity and streaming.

How to answer “Which one would you choose?”

  1. Is content public and mostly stable? Prefer prerendering.
  2. Can it be slightly stale? Add time-based or on-demand revalidation.
  3. Does it depend on the current user/request? Render the relevant part at request time and enforce authorization.
  4. Is a section slow? Put it behind a loading/Suspense boundary so the rest can render sooner.

The RSC payload is a compact description of the rendered Server Component output plus placeholders for Client Components and their props. It is what client-side navigations fetch instead of a full HTML document.

Partial Prerendering (PPR) idea

A route can serve a static shell instantly and stream dynamic holes (wrapped in <Suspense>) in the same response. In recent versions this model is tied to Cache Components; check your version's config before relying on it.

08 · Data fetching

In a Server Component, fetch directly with fetch, an ORM or a database client. Do not add a needless HTTP hop by calling your own Route Handler from a Server Component.

export default async function Page() {
  const response = await fetch('https://api.example.com/products', {
    // Choose caching/revalidation intentionally for your Next.js version.
    next: { revalidate: 300 },
  })
  if (!response.ok) throw new Error('Could not load products')
  const products = await response.json()
  return <ProductList products={products} />
}

Parallel vs sequential requests

// Parallel when requests are independent
const [user, orders] = await Promise.all([
  getUser(),
  getOrders(),
])

// Sequential only when the second depends on the first
const user = await getUser()
const permissions = await getPermissions(user.id)
  • Check response.ok; fetch does not throw just because the server returned HTTP 404/500.
  • Use request-time APIs such as cookies/headers only when needed; they can affect rendering behavior.
  • Use loading.tsx or a local <Suspense fallback={...}> around slow work.
  • Validate external/API data at boundaries; TypeScript types do not validate runtime JSON.
  • For client-side re-fetching, consider a client data library when caching, retries, polling or optimistic updates justify it.

Deduplicate and share data across a render

// lib/data.ts
import 'server-only'
import { cache } from 'react'

// One DB call per request, even if layout, page and
// generateMetadata all ask for the same user.
export const getUser = cache(async (id: string) => {
  return db.user.findUnique({ where: { id } })
})
  • Request memoization: identical GET fetch calls in one render pass are deduplicated; use React cache() for ORM/DB calls.
  • That memoization lives only for one request; it is not the cross-request Data Cache.
  • Streaming a promise: start a fetch in a Server Component, pass the promise to a Client Component and unwrap it with use() inside <Suspense>.

09 · Caching and revalidation

Caching is a policy decision: what can be reused, for how long, and how does it become fresh? Avoid saying “Next.js always caches fetch” or “never caches fetch” without specifying version/configuration.

Tag-based invalidation

// read
const products = await fetch(url, { next: { tags: ['products'] } })

// write (Server Action)
'use server'
import { revalidateTag, revalidatePath } from 'next/cache'
export async function addProduct(data) {
  await db.product.create({ data })
  revalidateTag('products')     // every fetch tagged 'products'
  revalidatePath('/products')   // or a specific route
}

Newer model: Cache Components

// next.config.ts → cacheComponents: true (Next.js 16+)
import { cacheLife, cacheTag } from 'next/cache'

export async function getProducts() {
  'use cache'
  cacheLife('hours')
  cacheTag('products')
  return db.product.findMany()
}

With Cache Components, dynamic is the default and you opt into caching with 'use cache'. Newer releases also changed invalidation helpers (e.g. a cache-life profile argument for revalidateTag, plus updateTag for read-your-own-writes in Server Actions). Confirm against your installed version.

Security rule: never cache private, user-specific data in a way that can leak it across users. Be explicit about cache keys, authorization boundaries and what is safe to reuse.

10 · Loading, not-found and error handling

Loading

loading.tsx or Suspense fallback. Show a useful skeleton or progress state.

Not found

Call notFound() when a resource does not exist; render a not-found.tsx UI.

Unexpected error

error.tsx creates a route-segment error boundary. It must be a Client Component.

// app/products/[id]/page.tsx
import { notFound } from 'next/navigation'

export default async function ProductPage({ params }) {
  const { id } = await params
  const product = await getProduct(id)
  if (!product) notFound()
  return <h1>{product.name}</h1>
}

Expected vs unexpected errors: expected cases such as validation failures should usually be modeled as return values/messages. Unexpected exceptions should be logged safely and handled by an error boundary. Event-handler errors are not automatically caught by React error boundaries—handle them explicitly.

// app/products/error.tsx
'use client'
export default function Error({ error, reset }: {
  error: Error & { digest?: string }
  reset: () => void
}) {
  return (
    <div role="alert">
      <p>Something went wrong loading products.</p>
      <button onClick={() => reset()}>Try again</button>
    </div>
  )
}
  • error.tsx does not catch errors from the layout.tsx in the same segment—put the boundary in the parent segment for that.
  • global-error.tsx catches root layout errors and must render its own <html> and <body>.
  • In production, server error messages are replaced with a generic message plus a digest you can match against server logs.
  • notFound() and redirect() work by throwing; do not swallow them in a broad try/catch.

11 · Forms, Server Actions and mutations

Server Functions are async functions that run on the server. When used for a mutation/form action, they are commonly called Server Actions.

// app/actions.ts
'use server'

export async function createPost(formData: FormData) {
  const title = String(formData.get('title') ?? '').trim()
  if (!title) return { error: 'Title is required' }

  const session = await getSession()
  if (!session?.user) throw new Error('Unauthorized')

  await db.post.create({ data: { title, userId: session.user.id } })
  // Revalidate the affected path/tag if required.
  return { success: true }
}
  • Validate all input on the server, even if the browser validates it too.
  • Authenticate and authorize inside each Server Action; it can be invoked via a direct POST, not only through your UI.
  • Use pending and error states for good form UX; do not expose internal stack traces or secrets.
  • Revalidate affected cached data after a successful write.
  • Use Route Handlers instead when you need a general HTTP API for other clients/webhooks or explicit HTTP methods.

Form UX with React 19 hooks

// app/posts/new/form.tsx
'use client'
import { useActionState } from 'react'
import { useFormStatus } from 'react-dom'
import { createPost } from '@/app/actions'   // (prevState, formData) => result

function SubmitButton() {
  const { pending } = useFormStatus()
  return <button disabled={pending}>{pending ? 'Saving…' : 'Save'}</button>
}

export function NewPostForm() {
  const [state, formAction] = useActionState(createPost, null)
  return (
    <form action={formAction}>
      <input name="title" required />
      {state?.error && <p role="alert">{state.error}</p>}
      <SubmitButton />
    </form>
  )
}
HookGives you
useActionStateAction's last returned state + pending flag; action receives (prevState, formData).
useFormStatusPending state of the parent <form>; must be used in a child component.
useOptimisticShow the expected result immediately, roll back automatically if the action fails.
useTransitionCall an action outside a form (e.g. a like button) with a pending state.
Progressive enhancement: a <form action={serverAction}> rendered by a Server Component can submit even before JavaScript loads. Validate with a schema library such as Zod and return field-level errors instead of throwing.

12 · Route Handlers, API design and Proxy

Route Handler — route.ts

Implement HTTP endpoints using Web Request/Response APIs. Supports GET, POST, PUT, PATCH, DELETE, HEAD and OPTIONS.

// app/api/health/route.ts
export async function GET() {
  return Response.json({ ok: true })
}

Proxy — proxy.ts

Runs before a request completes; can redirect, rewrite or change headers based on request data. In Next.js 16, Middleware was renamed Proxy.

Use it for lightweight request routing—not as your only authorization/security layer or for slow data fetching.

Choose the right tool

  • Server Component: read data on the server directly.
  • Server Action: mutate data from a form/action context.
  • Route Handler: expose an HTTP endpoint to browsers, external clients or webhooks.
  • Proxy: perform lightweight request interception/redirect/rewrite logic.

Route Handler with params, query and body

// app/api/products/[id]/route.ts
import { NextRequest } from 'next/server'

export async function GET(req: NextRequest, { params }: {
  params: Promise<{ id: string }>
}) {
  const { id } = await params
  const fields = req.nextUrl.searchParams.get('fields')
  const product = await getProduct(id, fields)
  if (!product) return Response.json({ error: 'Not found' }, { status: 404 })
  return Response.json(product)
}

export async function PATCH(req: NextRequest, ctx) {
  const session = await getSession()
  if (!session) return new Response('Unauthorized', { status: 401 })
  const body = await req.json()          // validate before use!
  // ...
  return Response.json({ ok: true })
}

Proxy example with a matcher

// proxy.ts (project root or src/) — was middleware.ts before v16
import { NextResponse, type NextRequest } from 'next/server'

export function proxy(request: NextRequest) {
  const hasSession = request.cookies.has('session')
  if (!hasSession) {
    return NextResponse.redirect(new URL('/login', request.url))
  }
  return NextResponse.next()
}

export const config = {
  matcher: ['/dashboard/:path*', '/settings/:path*'],
}

Proxy is an optimistic check (is there a cookie?). The real session verification and permission check still happen in the page, action or DAL.

Stateless session (JWT in cookie)

  • Signed/encrypted token holds user id + expiry.
  • No DB lookup per request; scales easily.
  • Hard to revoke before expiry; keep payload small.

Database session

  • Cookie holds an opaque session id.
  • Server looks up the session each request.
  • Easy revocation ("log out all devices"); extra lookup cost.
// lib/dal.ts — the single place that verifies sessions
import 'server-only'
import { cache } from 'react'
import { cookies } from 'next/headers'
import { redirect } from 'next/navigation'

export const verifySession = cache(async () => {
  const token = (await cookies()).get('session')?.value
  const session = await decrypt(token)       // jose / your auth lib
  if (!session?.userId) redirect('/login')
  return { userId: session.userId, role: session.role }
})

// app/dashboard/page.tsx
export default async function Dashboard() {
  const { userId } = await verifySession()
  const orders = await getOrdersFor(userId)   // scoped by owner
  return <OrderList orders={orders} />
}

Cookie settings to remember

  • httpOnly: true — JS cannot read it (XSS protection).
  • secure: true — HTTPS only.
  • sameSite: 'lax' — CSRF mitigation.
  • path: '/' and a sensible expires/maxAge.

ProxyOptimistic redirect only (cookie exists?). Never the only check.
LayoutAvoid relying on it: layouts do not re-render on every navigation.
Page / Server ComponentVerify session before reading private data.

DAL / DTOReturn only the fields the caller may see.
Libraries: Auth.js (NextAuth), Clerk, Better Auth, Supabase Auth, Auth0, Kinde, etc. Be ready to say what they handle for you (OAuth flows, session rotation, CSRF) and what still remains your job (authorization rules and data scoping).
Never store tokens in localStorage for a server-rendered app, never trust a role sent from the client, and always hash passwords with a slow algorithm (bcrypt/argon2).

14 · Security fundamentals

  • Secrets: keep API keys and database credentials server-side. Variables prefixed with NEXT_PUBLIC_ are exposed to browser bundles.
  • Authorization: check permissions close to the data access or mutation, not only in navigation/UI or Proxy.
  • Input: validate and normalize all untrusted input on the server.
  • Data exposure: return only fields the client is allowed to see; do not pass entire database records by habit.
  • CSRF / webhooks: use appropriate framework protections and verify signatures/authentication for integrations.
  • Redirects: validate user-controlled redirect destinations to avoid open redirects.
  • Errors/logs: never send stack traces, secrets, tokens or private data to users.
Golden principle: hiding a button is not authorization. Every read and write involving private data must enforce the correct access rules on the server.

Common attacks and the Next.js-shaped defence

ThreatDefence
XSSReact escapes output by default; avoid dangerouslySetInnerHTML or sanitize first; add a Content-Security-Policy header.
CSRFServer Actions only accept POST and compare Origin/Host; use sameSite cookies; protect custom Route Handlers yourself.
IDOR (accessing others' data by id)Scope every query by owner/tenant: where: { id, userId }.

16 · SEO, images, fonts and metadata

  • Metadata: export a static metadata object or use generateMetadata for data-dependent titles/descriptions. These exports are supported in Server Components.
  • Images: use next/image for sizing, responsive delivery and optimization; configure allowed remote image sources when needed.
  • Fonts: use next/font to optimize font loading and reduce layout shifts.
  • Social previews: configure Open Graph metadata and generated/static OG images.
  • Accessibility: semantic HTML, keyboard navigation, visible focus, descriptive alt text and clear loading/error states still matter.
  • Discoverability: add sitemap/robots configuration where relevant and ensure pages intended for search engines are crawlable.

17 · Performance and debugging

Rendering & bundle

  • Keep Client Components narrow.
  • Use Server Components for server-only work.
  • Lazy-load heavy client-only widgets when appropriate.
  • Inspect bundle size instead of guessing.

Network & UX

  • Parallelize independent requests.
  • Stream slow sections with Suspense.
  • Use loading skeletons that preserve layout.
  • Use Link/prefetch behavior appropriately.

Data & cache

  • Measure slow API/database calls.
  • Set intentional freshness and invalidation.
  • Avoid duplicate HTTP hops.
  • Check production, not just dev behavior.

Debugging checklist

  • Read server and browser console separately.
  • Check network status and response body.
  • Look for hydration mismatches.
  • Verify env vars, build logs and runtime logs.

Hydration mismatch examples: rendering different values on server and client (current time/randomness), reading browser-only state during initial render, invalid HTML nesting, or locale-dependent output. Make initial output deterministic and defer browser-only behavior to effects when appropriate.

Lazy-load heavy client widgets

'use client'
import dynamic from 'next/dynamic'

const Chart = dynamic(() => import('./chart'), {
  ssr: false,                       // browser-only lib (uses window)
  loading: () => <p>Loading chart…</p>,
})

ssr: false is only allowed inside Client Components. Server Components are already code-split automatically.

Node.js vs Edge runtime

Node.js (default)

  • Full Node APIs and npm ecosystem.
  • Best for DB drivers, ORMs, file system, heavy work.

Edge

  • Web-standard APIs only, smaller cold starts.
  • Limited packages and no native Node modules; check per-version support.

19 · Testing strategy

Unit

Vitest / Jest

Pure functions, validation schemas, DAL helpers, synchronous components with React Testing Library.

Integration

Actions & handlers

Call Server Actions / Route Handlers directly with a test DB; assert auth and validation paths.

E2E

Playwright / Cypress

Real browser against next build && next start; covers async Server Components, routing and caching.

// __tests__/nav-link.test.tsx (Vitest + React Testing Library)
import { render, screen } from '@testing-library/react'

  expect(screen.getByRole('link')).toHaveAttribute('aria-current', 'page')

// e2e/checkout.spec.ts (Playwright)
test('user can add to cart', async ({ page }) => {
  await page.goto('/products/1')
  await page.getByRole('button', { name: 'Add to cart' }).click()
  await expect(page.getByText('1 item')).toBeVisible()
})
Gotcha: async Server Components are not well supported by Jest/Vitest render utilities yet—test their logic in the data layer and cover the rendered page with E2E tests.
What to test first: authorization (user A cannot read/modify user B's data), form validation errors, 404 paths, and one happy-path E2E per critical flow (sign in, checkout).
