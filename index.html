00 · Installation and project setup

Yes—installation belongs in a complete learning path. The official docs recommend starting with create-next-app, then learning the App Router conventions.

Prerequisites

  • Comfort with HTML, CSS, JavaScript and React.
  • Install a supported Node.js version. The current installation guide lists Node.js 20.9+; verify requirements when upgrading.
  • Use a package manager such as npm, pnpm, Yarn or Bun.

Quick start with npm

npx create-next-app@latest my-app
cd my-app
npm run dev

# Open http://localhost:3000

The CLI asks about TypeScript, ESLint, Tailwind CSS, App Router, a src/ directory and import aliases. Current defaults can change; review the prompts instead of assuming every project is configured identically.

Files you should recognize

my-app/
  app/ or src/app/      # App Router pages and layouts
  public/               # static files served from /
  components/           # shared UI (optional convention)
  lib/                  # data, auth and helper code (optional)

  next.config.ts        # framework configuration (if used)

  tsconfig.json         # TypeScript configuration
Environment variable rule: keep secrets in server-only variables, never commit real secrets, and only use NEXT_PUBLIC_ for values that are safe to expose in the browser. Restart the dev server after changing environment configuration when required.

First run checklist

  1. Create the app and run npm run dev.
  2. Edit app/page.tsx and confirm hot reload works.
  3. Understand app/layout.tsx and the required root html/body.
  4. Create one route, one dynamic route and one shared component.
  5. Run lint/type checks and npm run build before deploying.

01 · Why Next.js?

Next.js is a React framework that adds routing, server rendering, data-fetching patterns, backend endpoints and production optimizations around React.

React alone

Primarily a UI library. You choose and assemble routing, rendering strategy, data patterns, SEO setup and build tooling.

Next.js

A framework with file-based routing, Server Components, server rendering, streaming, metadata APIs, image/font optimization and deployment conventions.

Why teams choose it

  • SEO and first load: server-rendered or prerendered HTML can make meaningful content available before client JavaScript finishes.
  • Flexible rendering: choose static/prerendered output or request-time data where the page needs it.
  • Full-stack workflow: use Route Handlers and Server Actions for appropriate backend tasks.
  • Performance defaults: route prefetching, streaming, image/font tooling and code splitting.
Interview answer: “I use Next.js when a React app benefits from integrated routing, server rendering, SEO metadata, data access and production conventions. I still choose the rendering and caching strategy per route instead of assuming every page should be static or dynamic.”

03 · Routing and dynamic routes

In the App Router, folders define URL segments; special files define what each segment does.

app/
  layout.tsx             # required root layout
  page.tsx               # /
  about/page.tsx         # /about
  blog/[slug]/page.tsx   # /blog/hello-world
  shop/[...parts]/page.tsx      # one or more segments
  docs/[[...slug]]/page.tsx     # zero or more segments
  not-found.tsx
  loading.tsx
  error.tsx
ConventionPurposeInterview note
page.tsxPublicly accessible UI for a route.Folder alone does not expose a page; a page/route handler is needed.
layout.tsxShared UI around child routes.Layouts preserve state and remain interactive across navigation.
loading.tsxSegment-level loading UI.Creates a Suspense boundary for the route segment.
error.tsxSegment error fallback.Must be a Client Component; catches errors in its child segment.
not-found.tsxNot-found UI.Use notFound() for a missing resource.
route.tsHTTP endpoint.Cannot coexist with page.tsx at the exact same route segment.

Read dynamic parameters

// app/blog/[slug]/page.tsx (current App Router pattern)
export default async function BlogPost({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const post = await getPostBySlug(slug)

  if (!post) notFound()
  return <article><h1>{post.title}</h1></article>
}
  • [slug]: one dynamic segment.
  • [...slug]: catch-all; requires one or more segments.
  • [[...slug]]: optional catch-all; also matches the parent path.
  • params describes path segments; searchParams describes query-string values like ?page=2.
  • Use Link for normal navigation; use useRouter for imperative navigation in a Client Component.

Other routing conventions worth knowing

  • (group) route groups organize files without changing the URL.
  • @slot defines a parallel route slot, useful for multi-panel layouts and independent sections.
  • (.), (..) and related intercepting-route conventions can render another route within the current layout context—useful for modal navigation patterns.
  • template.tsx is similar to a layout but remounts its children on navigation; choose it when fresh state/effects are required.
  • default.tsx provides a fallback for an unmatched parallel route slot.
  • generateStaticParams() can generate dynamic route params for prerendering. Understand its interaction with dynamic rendering and current caching features.
  • redirect() redirects during rendering/actions; useRouter is for imperative client navigation. Validate user-controlled destinations.
Common trap: In current App Router docs, params and page searchParams are promises—await them. Older tutorials may show synchronous props.

04 · Server Components vs Client Components

Server Component (default)

  • Runs on the server.
  • Can await data and query a database directly.
  • Can keep secrets server-side when used correctly.
  • Good for read-heavy UI and reducing browser JavaScript.
No useState / onClick

Client Component

  • Opt in with 'use client' at the file boundary.
  • Use state, effects, event handlers and browser APIs.
  • Its JavaScript is sent to the browser.
  • Good for interactive widgets, menus, forms and charts.
Interactive UI

Decision flow

Need state, event handlers, effects or browser APIs?
→
Yes
Client Component for that small boundary
No
Keep it a Server Component
// Server Component: app/products/page.tsx
import ProductFilter from './product-filter'

export default async function ProductsPage() {
  const products = await getProducts()
  return <>
    <h1>Products</h1>
    <ProductFilter products={products} />
  </>
}

// product-filter.tsx
'use client'
import { useState } from 'react'
export default function ProductFilter({ products }) {
  const [query, setQuery] = useState('')
  return <>
    <input value={query} onChange={e => setQuery(e.target.value)} />
    {/* render filtered products */}
  </>
}

Rule of thumb: keep the client boundary as low and small as practical. Server Components can render Client Components, and Client Components can receive server-rendered UI as children/props where serializable. Do not pass database clients, secrets or arbitrary non-serializable values to the client.

05 · SSR, SSG, ISR and CSR

TermWhen HTML/data is producedBest fitTrade-off
SSRAt request time on the server.Request-specific or frequently changing content.Server work on requests; latency depends on data.
SSG / prerenderingBefore requests, commonly at build time.Stable public pages.Needs a strategy to refresh stale content.
ISR / revalidationServe reusable output and refresh according to configured revalidation.Content that can be briefly stale.Understand freshness windows and on-demand invalidation.
CSRBrowser JavaScript fetches/renders data.Highly interactive, browser-only experiences.May delay meaningful content; SEO/initial loading needs care.
StreamingSend UI in chunks as parts become ready.Pages with slow or independent data sections.Requires good loading boundaries and thoughtful UX.

These are useful conceptual labels, not four mutually exclusive switches. A Next.js route can combine server rendering, prerendered pieces, client interactivity and streaming.

How to answer “Which one would you choose?”

  1. Is content public and mostly stable? Prefer prerendering.
  2. Can it be slightly stale? Add time-based or on-demand revalidation.
  3. Does it depend on the current user/request? Render the relevant part at request time and enforce authorization.
  4. Is a section slow? Put it behind a loading/Suspense boundary so the rest can render sooner.

06 · Data fetching

In a Server Component, fetch directly with fetch, an ORM or a database client. Do not add a needless HTTP hop by calling your own Route Handler from a Server Component.

export default async function Page() {
  const response = await fetch('https://api.example.com/products', {
    // Choose caching/revalidation intentionally for your Next.js version.
    next: { revalidate: 300 },
  })
  if (!response.ok) throw new Error('Could not load products')
  const products = await response.json()
  return <ProductList products={products} />
}

Parallel vs sequential requests

// Parallel when requests are independent
const [user, orders] = await Promise.all([
  getUser(),
  getOrders(),
])

// Sequential only when the second depends on the first
const user = await getUser()
const permissions = await getPermissions(user.id)
  • Check response.ok; fetch does not throw just because the server returned HTTP 404/500.
  • Use request-time APIs such as cookies/headers only when needed; they can affect rendering behavior.
  • Use loading.tsx or a local <Suspense fallback={...}> around slow work.
  • Validate external/API data at boundaries; TypeScript types do not validate runtime JSON.
  • For client-side re-fetching, consider a client data library when caching, retries, polling or optimistic updates justify it.
Interview signal: explain where data runs, how errors are surfaced, whether data is fresh or cached, and how you avoid waterfalls—not just the syntax of fetch.

07 · Caching and revalidation

Caching is a policy decision: what can be reused, for how long, and how does it become fresh? Avoid saying “Next.js always caches fetch” or “never caches fetch” without specifying version/configuration.

★ Must know · Error handling

08 · Loading, not-found and error handling

Loading

loading.tsx or Suspense fallback. Show a useful skeleton or progress state.

Not found

Call notFound() when a resource does not exist; render a not-found.tsx UI.

Unexpected error

error.tsx creates a route-segment error boundary. It must be a Client Component.

// app/products/[id]/page.tsx
import { notFound } from 'next/navigation'

export default async function ProductPage({ params }) {
  const { id } = await params
  const product = await getProduct(id)
  if (!product) notFound()
  return <h1>{product.name}</h1>
}

Expected vs unexpected errors: expected cases such as validation failures should usually be modeled as return values/messages. Unexpected exceptions should be logged safely and handled by an error boundary. Event-handler errors are not automatically caught by React error boundaries—handle them explicitly.

Interview question: Why use a nested error boundary? It lets a section fail with a fallback and recovery action without necessarily replacing the whole application UI.

09 · Forms, Server Actions and mutations

Server Functions are async functions that run on the server. When used for a mutation/form action, they are commonly called Server Actions.

// app/actions.ts
'use server'

export async function createPost(formData: FormData) {
  const title = String(formData.get('title') ?? '').trim()
  if (!title) return { error: 'Title is required' }

  const session = await getSession()
  if (!session?.user) throw new Error('Unauthorized')

  await db.post.create({ data: { title, userId: session.user.id } })
  // Revalidate the affected path/tag if required.
  return { success: true }
}
  • Validate all input on the server, even if the browser validates it too.
  • Authenticate and authorize inside each Server Action; it can be invoked via a direct POST, not only through your UI.
  • Use pending and error states for good form UX; do not expose internal stack traces or secrets.
  • Revalidate affected cached data after a successful write.
  • Use Route Handlers instead when you need a general HTTP API for other clients/webhooks or explicit HTTP methods.

10 · Route Handlers, API design and Proxy

Route Handler — route.ts

Implement HTTP endpoints using Web Request/Response APIs. Supports GET, POST, PUT, PATCH, DELETE, HEAD and OPTIONS.

// app/api/health/route.ts
export async function GET() {
  return Response.json({ ok: true })
}

Proxy — proxy.ts

Runs before a request completes; can redirect, rewrite or change headers based on request data. In Next.js 16, Middleware was renamed Proxy.

Use it for lightweight request routing—not as your only authorization/security layer or for slow data fetching.

Choose the right tool

  • Server Component: read data on the server directly.
  • Server Action: mutate data from a form/action context.
  • Route Handler: expose an HTTP endpoint to browsers, external clients or webhooks.
  • Proxy: perform lightweight request interception/redirect/rewrite logic.

11 · Security fundamentals

  • Secrets: keep API keys and database credentials server-side. Variables prefixed with NEXT_PUBLIC_ are exposed to browser bundles.
  • Authorization: check permissions close to the data access or mutation, not only in navigation/UI or Proxy.
  • Input: validate and normalize all untrusted input on the server.
  • Data exposure: return only fields the client is allowed to see; do not pass entire database records by habit.
  • CSRF / webhooks: use appropriate framework protections and verify signatures/authentication for integrations.
  • Redirects: validate user-controlled redirect destinations to avoid open redirects.
  • Errors/logs: never send stack traces, secrets, tokens or private data to users.
Golden principle: hiding a button is not authorization. Every read and write involving private data must enforce the correct access rules on the server.

12 · SEO, images, fonts and metadata

  • Metadata: export a static metadata object or use generateMetadata for data-dependent titles/descriptions. These exports are supported in Server Components.
  • Images: use next/image for sizing, responsive delivery and optimization; configure allowed remote image sources when needed.
  • Fonts: use next/font to optimize font loading and reduce layout shifts.
  • Social previews: configure Open Graph metadata and generated/static OG images.
  • Accessibility: semantic HTML, keyboard navigation, visible focus, descriptive alt text and clear loading/error states still matter.
  • Discoverability: add sitemap/robots configuration where relevant and ensure pages intended for search engines are crawlable.
import type { Metadata } from 'next'

export const metadata: Metadata = {
  title: 'Products | Example Store',
  description: 'Browse our product collection.',
}

13 · Performance and debugging

Rendering & bundle

  • Keep Client Components narrow.
  • Use Server Components for server-only work.
  • Lazy-load heavy client-only widgets when appropriate.
  • Inspect bundle size instead of guessing.

Network & UX

  • Parallelize independent requests.
  • Stream slow sections with Suspense.
  • Use loading skeletons that preserve layout.
  • Use Link/prefetch behavior appropriately.

Data & cache

  • Measure slow API/database calls.
  • Set intentional freshness and invalidation.
  • Avoid duplicate HTTP hops.
  • Check production, not just dev behavior.

Debugging checklist

  • Read server and browser console separately.
  • Check network status and response body.
  • Look for hydration mismatches.
  • Verify env vars, build logs and runtime logs.

Hydration mismatch examples: rendering different values on server and client (current time/randomness), reading browser-only state during initial render, invalid HTML nesting, or locale-dependent output. Make initial output deterministic and defer browser-only behavior to effects when appropriate.
